### Planner and metering repairs from the cycle-2 audit

- **Fixed:** A plan child's landing is now read as the hybrid signal the planner amendment specified, on both backends: a `thread_landed` event or a merged change pull lands it, a plain close with no change pull at all also lands it, and only a change pull that closed unmerged leaves it unlanded. Plan children closed by hand after their pull merged, and children with no pull request, no longer block their dependents forever or hold their plan open.
- **Fixed:** An amendment that adds or rewires a child onto a plan child that already closed without landing now gives the dependent the same `dag` block and `dependency_unlanded` notice the close path writes, on both backends, so `claim_next` never hands it out over work that never merged.
- **Fixed:** On Postgres, submitting a plan settles a retry before the spawn budget, as SQLite already did: the same claim replaying its keys at a full budget gets its children back, and a different plan gets the conflict listing them, not a budget refusal.
- **Fixed:** On SQLite, `submit_plan` and `amend_plan` run the parent, holder, replay and budget reads inside the transaction, as on Postgres, so a claim released mid-sequence cannot slip a plan past the holder check and a duplicate submit answers with the replay or the conflict instead of a raw constraint error.
- **Fixed:** A plan replay over REST and MCP now reports the stored plan's hold, read from the blocks standing on its children, instead of recomputing it from the retry's body, so a retry that drops the threat-model flag still answers `held: true` while the stored children wait.
- **Fixed:** A usage report whose uncached charge would overflow the rollups' SQL bigint arithmetic (prompt tokens times the input rate, plus output times the output rate, plus the rounding term) is now refused at the write by the shared validation, instead of being stored and breaking every rollup that covers it from then on.
