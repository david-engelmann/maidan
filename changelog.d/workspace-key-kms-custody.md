### Workspace keys can be held by AWS KMS

- **Added:** `MAIDAN_WORKSPACE_KEY_CUSTODY=aws-kms` gives each workspace key its own AWS KMS key (bound by encryption context), destroyed through `ScheduleKeyDeletion` when the key is rotated out or the workspace is erased or purged, so erasure is crypto-shredding even against backups. This replaces the instance KEK, instead of the instance KEK. Custody sits behind one async interface (local, AWS KMS, and a fake KMS for tests); every read opens the workspace keys its rows need through the custody that wrapped them before it maps them, and the rewrap pass moves keys from the old custody to the configured one. Unknown custody values refuse boot; a custody that refuses to destroy a key fails the erasure and changes nothing.
- **Changed:** the AWS SDK (KMS and S3) is built without default features and uses a ring-based HTTPS client, so the server and CLI images run on Debian 12's glibc. AWS profiles that use `credential_process` are no longer supported; pass credentials through the environment, a static profile, SSO, web identity or the instance role.
